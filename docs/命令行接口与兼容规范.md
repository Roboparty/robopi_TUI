# TUI 命令行接口与兼容规范

2026-10-29；协议 1，首次实现于 robopi-tui 1.1.0，Studio 0.6.0。这里规定公共调用约定；实机部署和验证结果另见 Studio 的改造记录。

## 1. 固定入口和版本关系

```bash
robopi-tui rpc --protocol 1
```

这是 TUI 自身的命令，无需运行 Studio，没有 HTTP 服务和额外网络端口。板端可执行文件安装到 `/opt/roboparty/bin/robopi-tui`，兼容链接为 `/usr/bin/robopi-tui`。不带 `rpc` 的原交互模式和 `--version`、`--list-features` 保留。

调用者选择协议 1。TUI 包版本、Studio 软件版本、任务实现版本与通信协议分别管理。新增任务、参数展示行和可选字段继续使用协议 1；任何新版实现都必须保留协议 1 的语义和输出适配。

每个进程从 stdin 读取一行 UTF-8 JSON-RPC 2.0 请求，从 stdout 输出一行响应后退出，输入上限 64 KiB。本用途要求请求带字符串或整数 id，不支持通知和批量请求。id 在响应中原样返回；stdout 不混入菜单或诊断文字。

板端只读示例：

```bash
printf '%s\n' '{"jsonrpc":"2.0","id":"read-1","method":"tasks.list","params":{}}' | robopi-tui rpc --protocol 1
```

电脑端启动 `adb -s <ADB序列号> shell /usr/bin/robopi-tui rpc --protocol 1`，把同样的 JSON 行写入该进程的 stdin。请求体是数据，不是上传或拼接执行的脚本。

## 2. 固定方法

| method | params | result |
| --- | --- | --- |
| `tasks.list` | `{}` | `protocol:1`、`methods`、`tuiVersion`、`identity`、`writable`、`tasks`。 |
| `tasks.describe` | `{"taskId":"can-check"}` | 单个任务描述。 |
| `snapshot.get` | `{}` | `{"snapshot":...}`，只读采集所有参数，软件源版本来自缓存。 |
| `jobs.start` | `{"taskId":"can-check","requestId":"UUID"}` | 创建/查询该 UUID 的任务对象。 |
| `jobs.get` | `{"jobId":"UUID"}` | 指定任务对象，包含可用事件和终态结果。 |
| `jobs.list` | `{"limit":20}`，limit 可省略，范围 1～100 | `{"jobs":[...]}`，按状态文件最近修改时间倒序的历史任务。 |
| `jobs.active` | `{}` | `{"job":...}`，无记录为 null；有记录可能已结束，须检查 state。 |
| `jobs.acknowledge` | `{"jobId":"UUID"}` | 人工核对后的中断任务确认，不修复、不重跑原任务。 |

`tasks.list` 中的 identity 包含 `machineId`、`bootId`、`hostname`、`uid`。`writable` 当前表示 root 且存在 `systemd-run`，不是对网络、空间或硬件状态的保证。

任务描述：

```json
{
  "id": "can-check",
  "title": "检查 HPM 四路 CAN",
  "requiresRoot": true,
  "parametersSchema": {"type":"object","properties":{},"additionalProperties":false},
  "resultFormat": "board-result-v1"
}
```

本次范围内任务均无外部业务参数。`jobs.start` 可附带 `arguments:{}`；非空 arguments 返回 INVALID_PARAMS，不允许调用者指定 shell 命令、APT 包、固件路径或刷写地址。参数形式已预留，后续新增带参数任务需要同时扩展 TUI 的任务描述、校验和持久执行实现；不要求改变现有方法，但当前 Studio 不生成新参数表单。

请求示例仅说明格式；提交写任务前由使用者确认任务目的和目标板：

```json
{"jsonrpc":"2.0","id":"submit-1","method":"jobs.start","params":{"taskId":"can-check","requestId":"c44f7fec-2d29-469c-9922-4e2ec1941d6b"}}
```

## 3. 现有任务与判定

| 稳定 taskId | TUI 业务 | 判据和边界 |
| --- | --- | --- |
| `packages-check` | 刷新已配置的 apt.roboparty.com 二进制源，再采集五包版本。 | 源刷新和查询成功即可完成；版本差异在明细中展示，不安装软件。 |
| `apt-upgrade` | 严格刷新板端软件源，普通全系统升级，允许新依赖、禁止移除。 | 执行成功后，五包版本与指定源不一致时为 needs_review。 |
| `hpm-flash` | 刷新源、安装/更新 roboparty-analyze，从其 dpkg 文件列表选择唯一 ethercanfd_*.bin，调用 /opt/roboparty/bin/flash_hpm.sh。 | 脚本成功、正常 HPM USB 连续两次出现、同一 HPM 的 can0～can3 全部识别。 |
| `can-check` | 只读检查 USB、驱动和四路 CAN 归属，再采集参数。 | 唯一正常 HPM，驱动 gs_usb，can0～can3 均属于该 HPM。 |
| `pipeline` | 升级软件、安装/刷写 HPM、验证 USB/CAN、采集最终参数。 | 步骤均成功；五包版本差异为 needs_review。 |

五包为 roboparty-base、roboparty-bms、roboparty-analyze、robopi-addon、robopi-tui，指定源 apt.roboparty.com，按 Debian 版本规则比较。全系统升级范围大于五包；本地版本高于源版本也属于差异，不自动降级。

HPM 正常 VID/PID 为 1209:2323，boot 模式为 34b7:0008。`can` 和“HPM四路识别”仍只判断 USB、驱动与四路归属。1.1.1 起，快照增加可选的 `canConfiguration` 与“HPM配置检查/各路配置”参数行，按 RoboPi2 默认值检查 UP、FD、1M/5M、MTU 72、发送队列 10000 和控制器 ERROR-ACTIVE（这是正常的主动错误检测状态）。明确不符显示 fail，信息不足显示 needs_review；不会配置接口、修改 base/udev 或发送 CAN 帧。

`can-check`、`hpm-flash` 和 `pipeline` 识别成功但配置异常/未确认时，任务整体为 needs_review。烧录脚本或 USB/四路识别失败仍按原逻辑中止；配置异常不会伪装成刷写失败。旧 `can` 字段及协议 1 的格式不变。HPM 验证不含 Flash 字节读回，也不证明电机通信；Studio 自身更新检查留在电脑端。

所有 jobs.start 和 acknowledge 当前要求 root；后台执行依赖 systemd。除 can-check 外的任务还检查 RoboPi2 板型及空间，按既有规则在日志空间不足时归档并清理已结束旧 analyze 会话，记录 details.logCleanup。当前日志与不满足清理条件的目录保留。

## 4. 响应、错误和退出码

成功响应包含 result，失败响应包含 error，二者互斥。例如：

```json
{"jsonrpc":"2.0","id":"read-1","result":{"job":null}}
```

```json
{"jsonrpc":"2.0","id":"submit-1","error":{"code":-32010,"message":"板端任务正在运行","data":{"code":"BUSY"}}}
```

| 数字 code | data.code | 含义 |
| --- | --- | --- |
| -32700 | PARSE_ERROR | 无效 JSON 或请求超过限制。 |
| -32600 | INVALID_REQUEST | JSON-RPC 请求结构无效。 |
| -32601 | METHOD_NOT_FOUND | 不支持该方法，仅该调用不可用。 |
| -32602 | INVALID_PARAMS | 缺少参数、类型不对或现有任务收到非空 arguments。 |
| -32001 | UNSUPPORTED_PROTOCOL | 未实现所请求的协议；当前支持 1。 |
| -32004 | UNSUPPORTED_TASK / NOT_FOUND | 未安装任务，或任务记录/所需文件不存在。 |
| -32010 | BUSY / INTERRUPTED_JOB / REQUEST_CONFLICT / UNSUPPORTED_JOB_FORMAT | 并发冲突、中断待核对、UUID 用于不同动作、持久状态格式不支持。 |
| -32003 | PERMISSION_DENIED | 权限不足。 |
| -32603 | INTERNAL_ERROR | 其他服务端异常；保留 message 作为诊断。 |

调用方按 `data.code` 分类，message 仅供展示，不解析中文语句。未知错误仍是失败，保留原始响应。

命令退出 0 表示请求处理成功，不表示任务通过；查询 failed 任务可以退出 0。错误响应退出 2。ADB/Python/启动失败可能没有合法 JSON，保留退出码、stdout、stderr，不判定成功。

## 5. 任务、结果和参数格式

任务保留字段 `jobId`、`requestId`、`action`、`identity`、`state`、`stage`、`sequence`、`summary`、`startedAt`。新增任务还含 `taskId` 和独立的 `stateVersion:1`；缺少 stateVersion 的旧任务按原有格式 1 读取。

state 固定为 queued、running、completed、failed、interrupted。终态含 outcome（pass、fail、needs_review、error）和 finishedAt。completed 仅表示流程结束，不能据此判定通过。events 返回最近至多 60 条事件，每项含 sequence、time、stage、message；不是完整历史日志。stage 允许扩展，按普通进度信息展示。

可用时 result 包含 outcome、summary、snapshot、details。异常/中断时 result 可能缺失；执行异常可带 errorCode=TASK_EXECUTION_FAILED。details 是动作相关的扩展证据，不应要求每个任务都有相同内部字段。

快照稳定格式名为 `board-snapshot-v1`：

- `format` 固定为 board-snapshot-v1；旧入口同时保留 schemaVersion=1。
- `identity` 包含 machineId、bootId 等身份，不能用 HPM USB serial 替代机器身份。
- `collectedAt` 是带时区 ISO 8601 时间。
- `parameters` 每项含 group、name、value（字符串）、outcome、collectedAt。允许添加任意参数行，不能依赖中文名称、行号、行数或排序解析业务。
- `softwarePackages` 每项含 name、installedVersion、latestVersion、status、source、architecture；status 是展示文本。
- can、packageError、raw 为补充结果与证据。raw 的内部采集结构不作为稳定前端模型。

调用者只展示自己理解的格式，忽略未知可选字段；未知 outcome 标记未确认，不默认通过。单条参数或包记录损坏时保留其他条目与原始证据。快照无法展示时仍保留任务身份、终态和任务结论，并明确提示缺少可展示参数。

## 6. 后台执行、重连与兼容

调用方先保存板卡身份和 UUID，然后提交一次 jobs.start，后续用 jobs.get 查询。重复 UUID、相同动作返回原任务；不同动作复用 UUID 失败。启动响应丢失后查询原 UUID，禁止换 UUID 自动再发升级/刷写。

关闭 Studio、停止等待或断开 ADB 不会取消板端任务。换板后拒绝采用原板结果。任务启动前冻结 loader/plugins 到私有任务目录，由 systemd 后台执行；目录继续使用 /var/lib/robopi-tui/studio-jobs，不搬移旧记录。

持久状态格式独立于通信/API版本；新版读取器继续支持旧格式 1。读取旧结果不依赖任务仍在当前目录中注册。板端重启或检测到任务异常退出时为 interrupted，人工核对后才 acknowledge；该操作不修复、不重跑。

兼容矩阵：

| 组合 | 行为 |
| --- | --- |
| Studio 0.6.0 + TUI 1.1.0 或继续提供协议 1 的新版 | 使用公共 CLI/JSON-RPC，忽略软件版本差异。 |
| Studio 0.5.0 + TUI 1.1.0 | 使用保留的 studio_api.py API v1 适配器，原命令及字段保留。 |
| Studio 0.6.0 + 已提供 API v1 的旧 TUI（本地 1.0.2～1.0.4） | 仅在公共 CLI 明确不存在或不认识 rpc 参数时回退旧入口。 |
| 旧 TUI 未提供任何任务后端（如原 0.1.2/1.0.1） | 对应任务不可用，需先安装提供后端的 TUI；Studio 不上传替代业务脚本。 |

收到合法 RPC 业务错误、无效响应或连接中断时不回退重发，以防重复任务。Studio 现有按钮按板端任务目录分别启用；目录查询失败保留独立采集到的参数。此版本不自动为新任务增加界面按钮，也不生成新参数表单。

## 7. 后续增加任务的开发约定

1. 在 TUI 内实现业务函数，使用既有 emit(stage, message) 报告进度，返回通用 outcome/summary/snapshot/details。
2. 在 loader/task_catalog.py 注册稳定 ID、名称和执行函数。当前无参任务使用 Task(id, title, execute)。无需修改 task_protocol.py 或 Studio 通信代码。
3. 使用 tasks.describe、tasks.list 验证注册，再通过同一个 jobs.start/jobs.get 执行。不要通过新增 shell 拼接逻辑让 Studio 接管业务。
4. 新增只读参数直接添加快照行，保持已有字段类型、单位、含义。新增可选字段、任务或行不提升协议版本。
5. 不删除或改名旧方法、旧任务 ID；不改变已有参数默认语义；新增必填参数需另建任务 ID 或保留旧调用适配。
6. 补充契约验证：旧请求仍有效、旧结果仍可读、未知扩展被忽略、单项不支持不影响其他方法、断线不重复执行。

协议确实需要破坏性修改时新增协议号，并行提供 --protocol 1 的适配器；不能只改一个全局版本常量后要求全部客户端同步升级。

代码分工：task_protocol.py 处理通信，task_catalog.py 注册任务，task_runtime.py 托管持久任务，board_backend.py 处理现有板卡业务，studio_api.py 仅兼容旧客户端。
